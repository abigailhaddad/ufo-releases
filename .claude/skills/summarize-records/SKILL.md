# Summarize UFO records

Each extracted-text file in `data/text/` corresponds to one record in `data/records.json` (the filename `<id>.txt` matches `record.id`). The goal is one markdown summary per file at `data/summaries/<id>.md`, generated by parallel subagents — one agent per file — so the main thread doesn't have to read multi-thousand-line OCR dumps.

## Procedure

1. **Ensure the output dir exists.** `mkdir -p data/summaries`.

2. **Build the work list.** List `data/text/*.txt`, list `data/summaries/*.md`, take the set difference by stem. Skip files that already have a summary so re-runs are incremental. If the user passed a specific id or range (e.g. `/summarize-records 1-10` or `35`), restrict to that.

3. **Load record metadata once.** Read `data/records.json` so you can pass each subagent the matching record's `title`, `agency`, `description`, `incidentDate`, `incidentLocation`. The text files are OCR with no header — the metadata is what makes the summary useful.

4. **Fan out in batches of 5–8 parallel agents.** In a single assistant message, emit multiple `Agent` tool calls (one per file in the batch). Use `subagent_type: "general-purpose"`. Wait for the batch to finish, then launch the next batch. Don't spawn 60+ agents in one message — that's wasteful if early ones reveal a prompt bug.

5. **After each batch**, print a one-line progress update (e.g. `batch 3/9: 8 done, 0 errored`). Don't read the summaries back — trust that the agent wrote the file. If an agent reports it couldn't write the file, retry that single file once, then move on and list it at the end.

6. **At the end**, do one pass to surface cross-file themes: scan the per-file `## Themes` sections (grep for `^- ` under `## Themes`) and report the 5–10 most recurrent themes to the user inline. Do not write a meta-summary file unless the user asks.

## Subagent prompt template

Each subagent gets a self-contained prompt. Substitute the bracketed values:

```
You are summarizing one declassified UAP/UFO record for a public mirror site.

Record metadata (from data/records.json):
- id: [ID]
- title: [TITLE]
- agency: [AGENCY]
- incident date: [INCIDENT_DATE]
- incident location: [INCIDENT_LOCATION]
- official description: [DESCRIPTION]

Source text file: [ABSOLUTE_PATH_TO_TXT]

Task:
1. Read the source text file in full. It is OCR output of a declassified document — expect noise, redactions ("[unclear: ...]"), and page markers ("--- PAGE N ---"). Do not transcribe it; synthesize.
2. **Track page numbers as you read.** The `--- PAGE N ---` markers correspond to the PDF's page numbers (1-indexed) and are the way readers will navigate back to the original. Every concrete claim you surface (a witness, a date, a sighting account, a quoted phrase) must carry a page citation in the form `(p. N)` or `(pp. N–M)` for content that spans pages. If a fact appears on multiple pages, cite the first occurrence. If the file has no `--- PAGE N ---` markers at all, note `**Source:** \`data/text/[ID].txt\` (no page markers — citations omitted)` in the header and skip page citations for this file only.
3. Write a markdown file to data/summaries/[ID].md with this exact structure:

   # [TITLE]

   **Record:** [ID] · **Agency:** [AGENCY] · **Incident:** [INCIDENT_DATE], [INCIDENT_LOCATION]
   **Source:** `data/text/[ID].txt` · **Pages:** N (where N is the highest page number seen)

   ## Summary
   3–6 sentences. What is this document, who wrote it, what does it actually contain or claim. Concrete over generic — name people, dates, places, aircraft, instruments where the text gives them, each with a `(p. N)` citation. If the file is mostly unreadable OCR, say so plainly in one sentence and stop.

   ## Key facts
   - Bulleted facts the reader can act on: dates, locations, witnesses, agencies involved, instruments, outcomes. **Each bullet must end with a page citation**, e.g. `- Sighting reported over Oak Ridge, TN by night-shift guards (p. 14)`. Skip the section if the document is too noisy to extract any.

   ## Themes
   - 3–7 short tags describing what is interesting or recurrent in this file. Use lowercase noun phrases, e.g. `radar-visual correlation`, `oak ridge sightings`, `green fireballs`, `interagency information sharing`, `witness credibility assessment`. Themes should be reusable — if another file discusses the same idea, it should pick the same tag. No page citations needed on themes.

   ## Notable quotes
   Optional. 1–3 short verbatim excerpts, each followed by `(p. N)`. Skip if nothing stands out.

3. Do not write anything outside data/summaries/[ID].md. Do not modify other files. Do not read other files in data/text/ — only the one assigned to you.
4. Reply with one line: "wrote data/summaries/[ID].md (NNN words)" or, on failure, "ERR: <reason>".

Constraints:
- No speculation beyond what the document says. If a sighting is reported, attribute it to the document, not to reality ("the report claims…", not "a UFO appeared…").
- Don't editorialize about UFO reality. The point is to make the record findable, not to argue.
- Keep the file under ~400 words total. These are index entries, not essays.
- Page citations must be real. If you can't pin a fact to a specific `--- PAGE N ---` block, leave the fact out rather than guess a page.
```

## Notes

- Filenames are stems-only (`1.md`, `35.md`, `163.md`) — match the `<id>.txt` source. Don't slugify titles into the summary filenames; the numeric id is the join key with `records.json`.
- Some text files may be 50 lines (mostly OCR garbage) and others 5000+ lines. The per-file agent absorbs that variance — the orchestrator never reads them.
- If `data/records.json` has no entry for a given text file id, still summarize it but note `**Record metadata:** not found in records.json` in the header.
- Don't commit the summaries unless the user asks.
